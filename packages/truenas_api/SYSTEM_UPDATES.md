# Native system updates: bounded TrueNAS 25.10 contract

The native workspace implements local boot/update readiness, an explicitly reviewed update-source check, available releases grouped by train, exact-release download, and a guarded install with **automatic reboot disabled**. This is not full WebUI update parity. It does not change update profiles/autocheck, support HA upgrades, select arbitrary trains or URLs, upload files, resume warnings, downgrade, reinstall the running version, or initiate reboot.

Implementation and fake-wire tests are pinned to the public `TS-25.10.1` middleware source. Stable 25.10 sessions and the required public method metadata are mandatory; missing permissions, job-shape mismatches and unsupported versions fail closed. No NAS check, download, installation, credential access or real mutation was used to develop or verify this slice.

## Public wire contract and effects

| Native step | Public RPC / exact argument shape | Interpretation and effects |
| --- | --- | --- |
| Local readiness | `system.version_short []`, `failover.licensed []`, `boot.get_state []` | Local version, HA licence and boot-pool state only. `system.info.version` uses the same short version; `system.version` is the different full name. |
| Boot identity and protection | `boot.environment.query [[], {"limit":129}]` | At most 128 environments; full name/dataset/creation/active/next-boot/Keep identity snapshot. No GUID is invented. |
| Conflicting jobs | `core.get_jobs [[["state","in",["WAITING","RUNNING"]]], {"limit":129,"select":["id","method","state"]}]` | At most 128 active jobs; boot, update, failover and power jobs block a new update operation. No job credentials, logs or raw errors are requested. |
| Explicit source check | `update.status []`, then `update.available_versions []` on NORMAL status | Contacts the configured update source, fetches manifests/release notes and updates server-side caches. `status` can initialize a previously null update profile in the database. These are **not automatic page-load reads**. ERROR is unavailable information, not “up to date.” |
| Exact release download | `update.download [train, version]` | Job receipt is an integer ID; owned job result must eventually be literal `true`. Creates staging directories, writes or reuses a shared image, may delete an old mismatching image, and may internally retry network transfers. No native replay is performed. |
| Guarded install | `update.run [{"dataset_name":null,"resume":false,"train":train,"version":version,"reboot":false}]` | Job receipt is an integer ID; owned successful result is literal `true`. Downloads/reuses staging, installs and selects a next-boot environment. The server's declared `dataset_name` option is currently ignored by `run`; no custom naming is promised. |
| Explicit owned-job progress | `core.get_jobs [[["id","=",id]], {"limit":2,"select":["id","method","arguments","state","progress","result"]}]` | Exactly one matching integer ID, method and complete normalized arguments are required. No periodic polling, foreign-job adoption, abort or retry endpoint exists in this slice. |

## Review, source identity and installation guards

Every operation starts from an inventory issued by this exact authenticated session. Review reads local safety state only, holds a five-minute single-use lease, and names the endpoint, currently running version and exact action/target. Wrong confirmation, a foreign/reused review, refresh, disconnect or changed safety state invalidates it. Flutter permanently expires an open review when its original session or inventory changes, including a transient disconnect that later restores the same object.

After confirmation, the SDK rechecks local state and performs the explicitly authorized source check. Download/install dispatch additionally requires the original exact train, version, filename, advertised SHA-256, compressed byte size and release profile to remain present. The current train/profile must also match. Release lists are bounded to 128 distinct entries; metadata is validated and immutable. Only strictly newer stable numeric versions in GENERAL or MISSION_CRITICAL release profiles are actionable. Same-version releases, downgrades, prereleases and unsupported profiles are inspect-only.

HA-licensed systems, conflicting jobs, unhealthy or actively scanning boot pools, unavailable boot selection, and a different next-boot environment are blocked. Installation additionally requires known nonzero raw boot free space, a target name absent from the boot inventory, and **Keep enabled on every inactive, non-next-boot environment**. Immediately before dispatch, the complete local identity/protection snapshot and capacity values are compared again.

Why Keep is mandatory: `ensure_free_space` can destroy unkept inactive environments, oldest first, **before internal image checksums and installer prechecks**. The client never calls this pruning operation itself and never silently changes Keep. Protecting all observed candidates removes that observed pruning opportunity; it does not reserve space or provide an external-race guarantee. [Installer and pruning order](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/update_/install.py), [run and manual behavior](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/update_/update.py).

## Honest space, progress and integrity reporting

Boot charts use the public `size`, `allocated` and `free` integers only when they are known, nonnegative, bounded and consistent. Zero stays zero; null is unknown. These are **zpool** quantities, not the boot-root dataset's `available` value. The public boot model excludes both `id` and `guid`. Environment identity is bounded by its public name/dataset/creation fields rather than an invented immutable GUID. [Boot model](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/api/v25_10_1/boot.py), [pool normalization](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/pool_/pool.py).

The server compares private boot-root dataset availability with the **internal uncompressed image size**. Public release `filesize` is compressed download size and cannot prove installation fit. Public dataset queries hide boot datasets, and public `filesystem.statfs` requires a `/mnt/...` path. The native UI therefore does not claim “enough space to install” from its boot chart; authoritative capacity and installer prechecks remain server-owned. [Dataset filtering](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/pool_/dataset_query_utils.py), [filesystem path restriction](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/filesystem.py).

Download percentage is only a server-reported progress value in 0–100, associated with a version. Null/out-of-range progress is never fabricated as zero, completed or an indeterminate operation. A successful download job or 100% progress is **not a staged-image integrity certificate**: an existing cached image receives SHA-256 verification, but a fresh transfer completes with length checks. Normal non-resume installation re-enters cache verification and performs internal checks, but can redownload, and accepts no expected-checksum argument. No public read-only staging hash or internal-image-size proof is exposed. [Downloader](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/update_/download.py), [image installation checks](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/update_/install_linux.py).

The update source URL can be configured in server-owned configuration. TrueRAID neither reads private configuration nor substitutes a client-supplied URL. It shows the server's bounded release metadata without independently attesting source provenance, transport trust or the downloaded artifact. There is no transaction/CAS joining source metadata, boot state and dispatch: another administrator, automatic downloader or source publication can race after the final check. [Source configuration](https://github.com/truenas/middleware/blob/TS-25.10.1/src/middlewared/middlewared/plugins/update_/utils.py).

## Job ownership and recovery

Submitting, unknown outcomes, owned pending jobs and an observed applied update participate in the shared SDK mutation fence and Flutter operation lock. A missing/malformed receipt, timeout, disconnect, malformed effectful check or ambiguous remote error never triggers automatic replay. Local refresh does not clear those fences.

An unknown poll retains the same owned job and remains manually pollable on the original session. Only exact terminal FAILED/ABORTED or verified SUCCESS releases that pending handle. A stopped job is not proof of rollback: partial staging or installation effects may remain, and the message requires inspection before a new plan. No server warning is automatically accepted and no `resume:true` call is sent.

Install SUCCESS additionally requires a healthy non-HA boot state, unchanged running version and active environment identity, all previous environments/protections preserved, and exactly one new environment selected for next boot with the requested version name. If that public observation is unavailable or uses an unexpected naming shape, outcome remains unknown—job success alone is not displayed as verified next-boot state. Successful installation, or explicit status `EREBOOTREQUIRED`, leaves this session write-fenced. Reboot is a separately managed TrueNAS action; no reboot RPC is emitted. Fresh connection acknowledgment preserves that prior completion is not a boot-success guarantee.

The connector-free preview uses immutable synthetic inventory and refuses check/download/install execution and job polling. Fake-wire and widget tests validate the contracts and UI boundaries, not actual appliance compatibility, successful boot or recovery readiness. Manual-file uploads, signature/provenance attestation, profile/autocheck editing, HA coordination, unattended scheduling, full train policy, controlled reboot and real-server acceptance remain open parity work.
