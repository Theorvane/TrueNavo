# TrueNAS WebUI parity: implementation ledger

## Current continuation: NQN-only editing of unassociated uncredentialed hosts

The native NVMe-oF page now changes an existing host NQN only when bounded public inventory proves the database ID is a host without subsystem mappings and a dedicated SDK read returns both DH-CHAP keys and DH group explicitly unset. The SDK privately reads one exact ID with a two-row boundary, validates null credentials and a known hash setting, and returns only ID/NQN/hash metadata; neither key-bearing rows nor raw failures leave that path. A five-minute endpoint-bound review requires identity-change consent and the exact host ID/old/new NQN phrase. Topology, public host inventory and protected target metadata are reread before submission. The SDK performs another protected preflight and submits only `nvmet.host.update(id, {hostnqn: newNqn})`; no key, group, hash or mapping fields are written. A fresh public and protected read must show the new NQN, unchanged hash, still-null credentials, no target mapping and all other projected inventory unchanged. Ambiguous outcomes or divergent readback fence further NVMe writes without retry; generic host update remains blocked. Editing an associated or credentialed host is unsupported. Sequential reads cannot exclude another administrator's race; initiator identity, runtime authentication and live access are not attested. The server reloads NVMe configuration, and initiators may require reconfiguration. Fake SDK-wire and app/widget tests only; no live NAS write occurred. See the official [host update contract](https://api.truenas.com/v25.10/api_methods_nvmet.host.update.html). TD-037 remains partial.
